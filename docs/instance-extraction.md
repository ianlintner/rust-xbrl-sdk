# XBRL 2.1 instance syntax extraction — milestone 3

Authority: XBRL 2.1 Recommendation 31 December 2003, corrected errata 20 February 2013, §§4.1–4.8, [normative text](https://www.xbrl.org/Specification/XBRL-2.1/REC-2003-12-31/XBRL-2.1-REC-2003-12-31+corrected-errata-2013-02-20.html), Appendix A; XML 1.0 5th edition; Namespaces in XML 1.0 3rd edition; XML Schema Part 2. This is **syntax extraction**, not XBRL validation or filing certification.

`xbrl_xml::instance::parse_instance(source, limits)` uses the bounded XML reader and returns `xbrl_core::instance::Instance` or a rule-coded diagnostic with source span. No schema/taxonomy is fetched. Successful extraction only means the supported syntactic subset was extracted; it does **not** mean the source is a valid XBRL document. The CLI parse command remains unimplemented.

Supported: direct item elements with expanded concept QName, raw lexical value or xsi:nil, optional ID, contextRef and unitRef; contexts with entity identifier/scheme, period date/dateTime or forever, and preserved segment/scenario extension subtrees; simple/product/divide units with expanded QName measures; decimals/precision (integer or `INF`); schemaRef href and root/element xml:base chain. Reference values and href targets are **not resolved**. Extension trees retain element names, attributes, direct text and child order, but interleaving of direct text and child elements is not round-trippable.

Fail closed: malformed XML, DOCTYPE, resource limits, missing required syntactic fields, invalid structure/date/accuracy/measure QName, unsupported tuple/complex/fraction items, linkbase/role/arcrole refs and footnotes. An unprefixed measure with no bound default namespace cannot be represented by the current `QName` type and is rejected; XML Schema QName semantics and such measure types need a future model extension. Numeric accuracy is represented in i64/u64; larger legal XML Schema integers report `unsupported` instead of being truncated.

Not implemented here: DTS membership and concept data types, context/unit reference target existence, duplicate ID handling, periodType compatibility, numeric value typing, fraction typing, nil type restrictions, unit simplification and currency restrictions, xml:base resolution, schema target validation, dimensions, footnote XLinks, tuple semantics, full date/dateTime lexical coverage (e.g. expanded years), mixed timezone duration ordering. Those belong to taxonomy/validation phases. Incomplete support must never be used as a green validity verdict.

Fixtures: authored `fixtures/instance/basic.xml` and 25 negative rows in `fixtures/instance/invalid.tsv`, each linked to clause families in `fixtures/instance/README.md`. Optional local extraction smoke uses six instances from XBRL International's XBRL 2.1 Conformance Suite 2025-07-16 (link and SHA-256 in fixture README); that archive was **not vendored** because its notice says all rights reserved. Run by unpacking it separately and setting `XBRL_21_SUITE_DIR` to the extracted `XBRL-CONF-2025-07-16` directory, then `cargo test -p xbrl-xml --test instance official_suite_extraction_smoke_when_explicitly_supplied`. These six extraction assertions are **not** full official conformance variations: official pass/fail/unsupported counts for the complete suite remain **0 run / not assessed**. In particular, the official 303-03/303-04 invalidities require taxonomy periodType checking and must not be counted as parser failures.
